# Changelog

Newest first. Each version starts with a `Date:` and a `Summary:` line; the README's What's new list is written from the newest three. Older entries have none.

## 0.10.0

Date: 2026-10-27
Summary: The dashboard page: projects, sessions and current phase with its loops, one local file rebuilt at every step, no network.

### Added
- The dashboard page, `skills/dashboard/scripts/page.mjs` (node built-ins and the collect script next to it, no network): `page.mjs --data <dir> [--out <file>] [--now <epoch ms>] [--no-fonts] [--refresh-s <5-300>]` writes `dashboard.html` in the data folder as one self-contained file. It shows a row for each project (closed, with a one-line summary; a project with a working or waiting session starts open) and inside it the sessions, each with the eight gates of a phase and its loops back, then a Roadmap part, an Estimate against actual part and an Archived sessions part. It is rendered on the server with plain string functions: every text is cleaned and escaped and goes only into element text or a double-quoted attribute, there is no JSON in the page, and no path the tool builds appears in it (text copied from your files is shown as written, and the known path forms of this machine are replaced, so do not put paths in plan text). The page carries a Content-Security-Policy with `default-src 'none'` and the SHA-256 of its one script, has no `src`, no outward link and no form, and its script makes no request. The page is written atomically, has a soft limit of 256 KB (above it, tables are left out, see below) and a hard limit of 1 MB (above it, the page is not written), never creates the data folder, and `--out` is refused inside the data folder under any other name or route (a link, a junction, or a network path such as `\\host\share`, on every platform).
- The loop arrows. Under the eight gates, a right-angled arrow (straight segments, square joins) goes from the gate a run left back to the gate it returned to, with its count (`x N`) and the two step names as text; a gate entered again says `round N`. Only the loop that is active right now moves; the rest are still, and none moves in print or with reduced motion. The animation restarts at each reload.
- The page refreshes itself every 10 s (`--refresh-s` sets 5 to 300), holds while you select text or hover a cut-off title, and has a Pause button. Its script keeps the clocks running, works out Idle and "No update" in the browser from the times in the page, and keeps the open state of each section, the scroll position and the focused row in `sessionStorage`, read back only as a true or false, a number or a checked key.
- The trail, an optional `trail` field in a session file (`[{ step, state, at }]`, at most 40 entries): `status.mjs set` appends an entry when the step or the state changes, and a run after `done` starts a new trail. `collect` uses it for new fields on each session (`loops`, `rounds`, `visits`, `workedMs`, `elapsedMs`, `estimateH`, `archived`), for `estimateH` on each roadmap phase and for a `summary` on each project.
- Fonts: PW Sans and PW Mono, subsets of IBM Plex Sans and IBM Plex Mono under the SIL Open Font License 1.1, renamed because the licence reserves the name "Plex". They are embedded in the page as `data:` urls; the licence text is `skills/dashboard/assets/OFL.txt`, and `--no-fonts` leaves them out. The assets are `assets/page.css`, `assets/client.js` and the two `.woff2` files.
- The `page` mode of the dashboard skill (`/phased-shipping:dashboard page [refresh seconds]`): builds the page and tells the owner where the file is.
- A test file, `tests/dashboard-page.test.mjs`, for the trail, the new collect fields, the page, the rebuild and the personal copy.
- The repository is the project. `status.mjs set`, `clear`, `register` and `unregister` take the folder that holds `PHASES.md` as `--root`, resolve it with `realpath` and walk up from it (itself first, then each parent, at most 40 folders) to the nearest folder with a `.git` entry, a folder or a file, found by name only (never opened, read or followed). The climb stops at the home folder and at the filesystem root and ignores a `.git` there; with no repository the folder itself is the project; a repository root that is the data folder, inside it or holding it is not used. The id is still the first 12 hex digits of the SHA-256 of the project root's real path, so a repository root that was already registered keeps its id, and existing entries are never migrated (a command that does not change the list leaves `projects.json` as it is; a stored roadmap that is text but not a usable path, such as one written by an earlier version inside `node_modules`, is ignored when the list is read, so it stops no command, and a command that writes the list anyway writes it without that entry, and without a repeat of a path already listed). A run in a subfolder that holds a `PHASES.md` adds its path from the project root (such as `docs/roadmap/PHASES.md`) to the project's roadmaps, and a `register --roadmap` value is relative to the project root. `main(argv, io)` takes `io.homedir` for the test seam.
- The logo's look on the page. In progress is the logo's salmon with its diagonal hatch (the dark page `#FFB28F`, the light page the light logo's `#B33A0B`, as the pale one is 1.6:1 there), on the running gate of a session and on the in-progress mark of a roadmap row, and the hatch drifts slowly (CSS only, no second script) wherever something is in progress; it moves by transform on a clipped layer, which a browser can animate off its main thread, and a page with more than 25 moving things keeps only the header rule and the running gates moving (a `calm` class decided in the page builder). The header rule is a salmon stripe that flows only while a session is working (a `has-working` class decided in the page builder) and is the same stripe, still, otherwise. The salmon is used only on borders, strokes and hatching. Motion is declared only for a screen with no reduced-motion request, so it is off with reduced motion and in print, and the Pause button stops it (a `paused` class). "Waiting for you" keeps its square stamp and gets its own accent (a rose on the dark page, a crimson on the light page).
- A slim roadmap bar on each project row, as the logo's three squares: shipped (filled), in progress (hatched, moving), planned (outlined), in proportion to the counts, with a text label (`3 shipped, 1 in progress, 3 planned`) that is also its `aria-label`; parked phases are named in the label and not drawn.
- Real figures in the page's title block: written (UTC), projects, phases shipped of all phases, sessions active and waiting for you, archived sessions and the source.
- Strict roadmap display. The page draws only standardized roadmaps: a roadmap file is standard when it has at least one table and every table has the `<!-- phased-shipping:roadmap v1 -->` marker line. `collect` gives each roadmap a `standard` field (additive, the schema stays `v: 1`; a reader that does not find it treats the file as not standard) and each project's `summary` gains `legacyFiles` (how many files are not standard) and `legacyNames` (their relative names, cleaned, at most 10). A project with files that are not standard shows one note inside it, `N roadmap files not standardized: <names> (not drawn). Standardize them with the roadmap skill, mode standardize.`, and its row says `(N not standardized)` after the number of roadmaps; a project with no standard file also shows `No standardized roadmap yet.` in its Roadmap part and has no roadmap bar. Its Estimate against actual part still shows from the history.
- A test that the hatch tile, the drift of the hatch and the drift of a gate's stripes are the same whole period, and that the stripe angle is the same in the stylesheet and in the strokes of a gate.
- Sessions are kept per roadmap and phase. A session file is now `sessions/<id>-<tag>+<phase>.json`, where `<tag>` is the first 6 hex digits of the SHA-256 of the roadmap path (in lower case only where the file system ignores letter case: Windows and macOS by default, `io.caseInsensitive` is the seam; on Linux `Docs/PHASES.md` and `docs/PHASES.md` are two roadmaps), and it has a `roadmap` field (the path of the roadmap file the run is for, relative to the project root). The `+` cannot occur in a phase id, so a name never reads as the older name of another phase, and the phase in a file name is lower case (a name with a capital in it is skipped and reported by base name). Two roadmaps in one repository that share a phase id no longer overwrite one session file, show each other's title, estimate or state, or extend each other's trail; `clear` removes only its own file. A run in a folder whose roadmap path is not usable (more than 5 folders deep, or a folder name with a character that is not allowed) gets a file of its own too: `sessions/<id>-u<tag>+<phase>.json` (a literal `u` before the tag, so no unlisted name is ever the name of a listed roadmap's file), no `roadmap` field, `"unlisted": true`, and a tag of a fixed text and the folder's path, so two such folders do not share a file; it has no listed roadmap, no title and no estimate. The collector requires the `u` in the name exactly when the marker is there and a `roadmap` field exactly when it is not; any other mix is skipped and reported by base name. A `set` or `clear` only ever reads, writes or removes its own file. The older form (`<id>-<phase>.json`, no roadmap field) is read by the collector and is never written, taken over or removed by `set` or `clear`; it ages out as Idle and is then archived like any session, and when an older file and a tagged file exist for the same project and phase only the newer one by `updated` is shown (the other is dropped without a word), so a phase is not listed twice. Each session in the merged JSON has a `roadmap` field (null for the older form, `(unlisted:<tag>)` for an unlisted folder), and its `estimateH` is that roadmap's row; a session with no roadmap field, or one that names a file the project does not list, takes the first standard roadmap that has the phase id.
- `status.mjs` stops at a `.git` that another user owns, where the system has user ids (`io.getuid` and `io.lstat` are the test seams), refuses a `--root` inside a `.git`, `node_modules` or `.roadmap-backups` folder of the project (exit 1, nothing written), no longer adds the project root's own `PHASES.md` when it found the root by climbing, and prints one extra line, in fixed words and never with a path, when a roadmap was not added (more than 5 folders deep, a folder name with a character that is not allowed, or ten roadmaps already). A roadmap entry with such a folder in its path is refused by the collector too.
- The page counts only what it can trust: a summary number that is not a whole number of zero or more is counted again from the rows it draws, a written time that is missing or unusable shows as `unknown`, and sessions of projects that are not listed are not counted. The roadmaps, phases and shipped figures are never more than the rows the page draws (the smaller of the summary's figure and the drawn count is shown).
- The session limits of the merged JSON. Only session files of listed projects count (files of a project that is not listed no longer push live sessions out). Every such file name is looked at with an `lstat`, and only the newest 250 by modified time are opened, so a data folder that only grows reads a bounded number of files (the newest 250), and only listing the folder grows with the number of files. Past 100 sessions the 100 with the newest `updated` time are kept, and a clock-skewed session counts as the oldest, so it cannot push live ones out. One entry in `errors`, a fixed phrase with the number left out and no file name, says how many sessions the cap left out, and a separate note (`notes`, shown on the page as a quiet note, not as an error) says how many older files were not opened. The cap is 100 so that a page with 40-entry trails and long names stays under its 1 MB limit.

### Changed
- The `summary` of a project counts standard roadmap files only: `roadmaps`, `phasesTotal` and `phasesShipped` leave out files that are not standard (their data is still in `roadmaps`). The Roadmap figure in the page's title block, the phase counts and the roadmap bar count the same files, and the titles in the Estimate against actual table come from standard roadmap rows only (the id alone otherwise).
- `status.mjs` rebuilds `dashboard.html` in the same process after a `set`, `clear` or `unregister` that worked while the dashboard is on (`disable` leaves the page as it was last written), with the one script next to it. While the dashboard is off nothing is built. A page that cannot be built prints one line, `page not rebuilt (<reason>)`, with an error code or a short fixed phrase and never a path, and the status call still exits 0.
- The dashboard skill no longer says the page arrives with a later version, and the onboard skill's checklist line for the dashboard now reads "Dashboard data: turn it on with `/phased-shipping:dashboard enable`, then open the page with `/phased-shipping:dashboard page`".
- The lint treats `.woff2` as a binary file, so the font bytes are not scanned as text.
- A big page degrades instead of freezing: over the soft limit of 256 KB, the Roadmap and Estimate tables of projects with no working or waiting session become one note line each (largest saving first); if the page is still over, the tables of the projects with a running session go the same way (a project's row, its sessions, a waiting one always, and its archived sessions stay), and a visible line says so; the hard limit is 1 MB, above which the page is not written. The two fonts are checked by a test that reads their name tables: PW Sans and PW Mono, PostScript names `PWSans-...` and `PWMono-...`, with only the copyright and licence records keeping the Plex notice.
- Smaller fixes to the page: the policy hash is taken over the script with LF line ends (the text a browser hashes); an `--out` with a colon in the file name is refused on every platform; a phase rolled back and shipped again shows its newest history record; with JavaScript off the Pause button and the refresh text (in the header and in the footer) are hidden, and the 90-minute stale banner, the refresh, Pause and the clocks need JavaScript; a cut-off title inside a summary is no longer focusable; a bad stored value no longer stops the page script from starting (each restore step stands alone); and after `unregister` a session file of the removed project is neither read nor reported, so it leaves no trace on the page.
- The stale-page banner appears after 90 minutes without a rewrite, the same time as the per-session "No update" warning (a long build step makes no status call, so a shorter time showed it during a healthy run). The page's `data-page-stale-min`, the banner's placeholder and the script's default come from one value.
- The title block no longer says "Sheet 1 of 1".
- The Estimate against actual table is built from the history log: the newest record of each phase with an `actual_h` (its `est_h`, else the roadmap row's calibrated estimate; its title from the roadmap row with that id, else the id alone), then shipped roadmap rows with an Actual and no history record. A roadmap with no Actual column filled now shows its history. The summary reads "N phases with a time", the empty state reads "No phase has an actual time yet.", and the page-size rule counts these rows. History actual hours come from timestamps and include any time spent waiting for the owner.
- No guard rule changed. The guard version is 0.10.0, kept equal to the plugin version, and the guard still has four roles (`builder`, `checker`, `shipper` and `model-scout`). The page is built by the status script and the page script, not by an agent.

## 0.9.0

Date: 2026-10-27
Summary: Dashboard data: opt-in status files at each gate, a local project list, and one merged JSON.

### Added
- The `/phased-shipping:dashboard` skill (owner-invoked only; sonnet, low): `enable`, `disable`, `state`, `list`, `register`, `unregister` and `collect`. The dashboard is off until the owner says yes. The page that shows the data arrives with the next phase; this version builds the data layer only.
- The status script, `skills/dashboard/scripts/status.mjs` (node built-ins only, no network): `state`, `enable`, `disable`, `asked`, `register`, `unregister`, `list [--paths]`, `set` and `clear`. It keeps three files in the data folder: `dashboard.json` (on or off, whether the question was asked, and two thresholds), `projects.json` (the list of projects, at most 100) and one `sessions/<id>-<phase>.json` per running phase (at most 16 KB). `projects.json` is the only place an absolute path is written, and `list` prints it only with `--paths`. The opt-in is enforced in the script: while the dashboard is off or was never turned on, `set`, `clear` and the automatic registration are a silent no-op (exit 0, one line, nothing written), `register` exits 1 and says to enable it first, and only `enable`, `disable`, `asked` and `unregister` write (`unregister` only removes an entry from the list, so it works while the dashboard is off). `--data` must be an absolute path: an empty or relative one is a usage error (exit 2) and nothing is read or written. Phase ids are lower-cased in the session file name, so `7a` and `7A` are one file. A session file name is built only from the 12-hex project id (a hash of the project's real path) and a phase id that matches `[A-Za-z0-9._-]{1,40}` and is not only dots, so no other text reaches a path. Text is cleaned (control, line-separator, bidirectional, zero-width, tag and other format characters become spaces, one line, capped). The data folder and each file must be a real folder or a regular file with one name: a link, a junction or a hard link makes the script stop and write nothing. Every write is a temp file in the same folder, flushed, then a rename (retried on Windows), so a failure leaves the old file whole.
- The collect script, `skills/dashboard/scripts/collect.mjs` (node built-ins and the roadmap reader next to it): `collect --data <dir> [--out <file>] [--now <epoch ms>]` merges the listed projects' roadmaps (through the roadmap skill's `parseRoadmap` and `toReadJson`), the timestamps in their plan files (`parsePlanFile`), the phase history joined only by the labels stored with each project, and the running sessions into one JSON (schema `v: 1`, in `references/status.md`). A roadmap or plan file is read only when its real path is inside the project, it is a regular file (not a link, not a hard link) and it is at most 256 KB; a file that fails is reported by base name and reason, and the rest still loads. A folder that moved shows as `not found` and stays listed; nothing is ever removed. A session is shown as `Working`, `Waiting for you`, `Done` or `Idle` (no update for 180 minutes), with a `noUpdate` flag for a working session quiet for 90 minutes, and a warning when one project has more than one open session. A bad session file is skipped and named by base name only. No path the tool builds is in the output; text copied from your files is shown as written, cleaned, with the known forms of this machine's registered project paths, the data folder path and the home folder path (in any mix of slashes, doubled backslashes or URL-encoded), and of `<drive>:\Users\<name>`, `/c/Users/<name>`, `/Users/<name>` and `/home/<name>`, replaced by `[path]` (inside string values only, never keys); invisible characters are removed first when that reveals a path, and other spellings of a path may remain, so don't put a path in plan text. `--out` is refused (exit 2, nothing written) when its folder is the data folder or inside it, or when a real path is already there that is not a regular file. Every text value is cleaned and is untrusted plain text for a page to show with `textContent`; `<`, `>`, `&`, U+2028 and U+2029 are written as `\u` escapes, so the JSON is safe to inline in a script and parses to the same values. The output is capped (100 projects, 200 sessions, 300 phases and 500 history records per project, 2 MB). Each file is opened once and checked through the open descriptor (a regular file with one name, at most the cap) before it is read, and a plan file under a `.git`, `node_modules` or `.roadmap-backups` folder is refused. A session whose time is more than 5 minutes ahead of the clock (or whose step started after its update) is shown as `Idle` with `noUpdate` and a `clock skew` warning. The reader module is chosen by the script's own folder name: `../../roadmap/` from a folder named `dashboard`, `../../ps-roadmap/` from one named `ps-dashboard`, and the script stops under any other name.
- A skill eval, `dashboard-opt-in-asks-once` (15 evals in all). It has not been run against a model yet.
- A test file, `tests/dashboard.test.mjs`, for both scripts, including a test that installs the personal copies into a temporary Claude home and runs the personal `collect.mjs` from `ps-dashboard`.

### Changed
- The run skill asks once, with AskUserQuestion, at the first run after this version whether to turn the dashboard on (the default answer leaves it off), and remembers the answer. While it is on, the run makes one `status.mjs set` call at each step (baseline, build, a check-in, compare, review, approve, ship, prod check, and `done` at the close). A call is a silent no-op when the dashboard is off, and a failed call never fails a gate. For the status calls this version adds, the command line holds only the phase id and the label (each matching `^[A-Za-z0-9._-]{1,40}$`, written without quotes, otherwise the call or the `--label` is left out), fixed step and state words, and the project folder in single quotes (the call is skipped when the folder's path holds a single quote, a control character or any of U+2018 to U+201B); the skill tells the run to put no title or other text from a file on it, and the run no longer passes `--name`. The dashboard skill follows the same rule for its own command lines (folder, label, id, `--roadmap` and `--out`).
- The onboard skill's checklist line for the dashboard now reads "Dashboard data: turn it on with `/phased-shipping:dashboard enable` (the page arrives with the next phase)".
- `sync-personal.mjs` also installs the dashboard skill as `ps-dashboard` and rewrites its sibling path in the run skill.
- No guard rule changed. The guard version is 0.9.0, kept equal to the plugin version, and the guard still has four roles (`builder`, `checker`, `shipper` and `model-scout`). The status calls are made by the main session, not by an agent.

## 0.8.0

Date: 2026-10-27
Summary: Onboarding: survey a project with your consent first, then standardize, adopt or start a roadmap.

### Added
- The `/phased-shipping:onboard` skill (owner-invoked only; sonnet, low): the first run in a project. It says what will happen and what is never read, runs `survey list`, asks the owner which files with AskUserQuestion, runs `survey run` with the digest of the confirmed list, shows the findings and how the plan will adapt, runs `survey classify`, asks which path to take (standardize, adopt, both or fresh) and ends with a first-run checklist (survey, roadmap, dashboard shown as "arrives with the dashboard phase"). It never writes a roadmap.
- The survey script, `skills/onboard/scripts/survey.mjs` (node built-ins only, no network): `list [--json]`, `run --confirm <list.json> | --all-listed --list-digest <digest> [--exclude <path>]...`, `show`, `classify`, `decline` and `leftovers`. An allowlist says what may be opened (README, CONTRIBUTING, CLAUDE.md, AGENTS.md, `docs/` Markdown, manifests, CI workflows, deploy config, plan files and roadmap tables) and a never-list says what may not (source code, `.env*`, keys, `.npmrc` and other credential files, databases, `.git`, `node_modules`, build output, lockfiles, files over 256 KB, binary files). `list` reads only folder entries and sizes. `run` reads only the confirmed files and exits 1 with nothing read when it is not given the owner's confirmation. A file whose text matches a known secret shape (token and key formats, private keys, passwords, `Bearer` and `Authorization` values, URL credentials, cloud keys, and a secret-looking name followed by a value; checked as written, with escapes decoded and as parsed JSON values) is skipped whole and counted, never printed; as a last check the finished survey and every printed line are scanned again and a match exits 1 with nothing saved or printed. The patterns catch known shapes, not every secret. No command body is kept anywhere: a script is its name and the command that invokes it, and a workflow is job, action and secret names plus a count of run steps (no run line and no word of one). The summary holds no script body, no run line and no line of any file; the project name, workflow and job names and a package's name are text from the files, cleaned to one line of plain text and cut short. A locked file is skipped once and never retried. Caps: 200 files, 64 KB per file, 400 KB in total. Symbolic links and junctions are never followed. No absolute path is printed or saved.
- The survey is saved in `.phased-shipping/` inside the project (`survey.json` with `v: 1`, `state.json`, and a `.gitignore` whose only line is `*`). The folder is created fail closed: if it is a file or a link, or its `.gitignore` is not `*`, nothing is written. There is one mode: the script reads the project files, and the model sees the summary the script prints. The skill's instructions (not a lock) keep the assistant from reading other project files or handing any to another agent.
- `list` prints a digest of the listing (a hash of the sorted paths and sizes). `run --all-listed` needs it as `--list-digest` and exits 1, reading nothing, when the files changed after the list. A `--confirm` file (at most 64 KB) never widens the list; entries not on the current list are only counted. `show` keeps only the schema's fields, cleaned and capped (control, line-separator, bidirectional, zero-width, tag and other Unicode format characters become spaces), keeps a command, an action, a stack entry and a manifest or deploy file name only in the forms the script itself writes, and says the survey was read from disk. In the survey and in `adopt`, a hard-linked file is skipped and counted (a second name may lead outside the project), and so is a folder link inside `docs/` or a plan folder. `adopt` writes only to a regular `.md` file outside `node_modules`, `.git`, build output, `.roadmap-backups` and `.phased-shipping`, skips a file or folder whose name holds a control, bidirectional, zero-width, tag or other format character, and plain-text-cleans titles from plan files (the same characters).
- `adopt`, a new `roadmap.mjs` command and a fourth mode of the `/phased-shipping:roadmap` skill: it reads a project's plan files (`phase-*.md`) and proposes roadmap rows for what they prove (id and title from the first heading; a status only from a real `Timestamps` line). A plan file with no real timestamps is listed as undecided and is added only when the owner gives it a status. It joins the phase history only for project labels the owner picks, refuses to propose rows while a roadmap table is still legacy (or accepts `--into`), never overwrites a roadmap, and writes only with `--write` through the same backups and checks as `standardize`.
- Real-world status forms in the reader: `shipped 2026-10-24`, `shipped 2026-10-25 (2nd attempt)` and `**shipped 2026-10-26** (plan: docs/phases/phase-x.md)` are placed; `confirmed`, a bare number and any other word stay blocked for the owner to choose.
- Two skill evals, `onboard-needs-consent` and `adopt-needs-yes` (14 evals in all). They have not been run against a model yet.
- A test hygiene check: every test file that makes a temp folder also removes it.

### Changed
- The plan skill offers onboarding once, with AskUserQuestion, when a project has no saved survey, and remembers a no in `.phased-shipping/state.json`. When a survey exists it uses the commands in it only as proposed hints, still asks the owner to confirm each one, never runs a command found in the survey and never runs the survey itself.
- `sync-personal.mjs` also installs the onboard skill as `ps-onboard`, and rewrites the sibling path to the survey script for the personal plan copy.
- No guard rule changed. The guard version is 0.8.0, kept equal to the plugin version, and the guard still has four roles (`builder`, `checker`, `shipper` and `model-scout`).

## 0.7.1

Date: 2026-10-26
Summary: Every roadmap write keeps a way back: the first version is kept for good, with undo and restore.

### Added
- `.original`: before the first write of any kind, `roadmap.mjs` keeps the roadmap file as it found it, as `<file>.original` in `.roadmap-backups/`. It is created once (never overwritten) and the script never renames or deletes it. A `.original` that is a directory or a symlink makes every write fail closed.
- `.prev`: `set` now keeps the file as it was before the change as `<file>.prev` in the same folder, replaced each time through a temp file and a rename. In 0.7.0 `set` kept nothing.
- `restore`, a new command (and a third mode of the `/phased-shipping:roadmap` skill, still owner-invoked only): `restore <file>` lists the kept copies (and any `<file>.bak-*` copy that 0.7.0 left beside the file, marked `legacy`); `restore <file> --from original|prev|<name>` prints what would change and writes nothing; with `--write` it first saves the current file as `<file>.before-restore-<timestamp>`, so a restore can be undone. A name with a slash, a backslash or `..` is a usage error; there is no way to name a path.
- The changed-while-writing check: just before each rename the script reads the roadmap file again, and if it changed since the command read it, it stops with exit 1 and changes nothing (`the roadmap changed while it was being written; nothing was changed, run again`). It narrows the window when two sessions write one file; it is not a lock.
- Copies fail closed: if a copy cannot be made, nothing is written to the roadmap and the exit code is 1. Every copy is written from the bytes the command read, with no overwrite.
- Copies are whole or absent: each is written under a temporary name, flushed to disk, then given its final name with a hard link, so `.original` (and the dated copies and the folder's `.gitignore`) never exist half written. Where a link is not possible (FAT, exFAT, some network drives) a `<copy>.incomplete` marker is made first and removed last; a marker left behind makes every later write refuse (exit 1, nothing written) until the owner has looked: for an `.original` marker, compare `.original` with the roadmap and delete it too if it is shorter, different or in doubt (it is made again), then delete the marker. A failed in-place copy keeps its marker whenever anything is left at the final name.
- On Windows a rename that is refused for a moment (a scanner or indexer holding the file) is retried up to 10 times, each time after the same changed-while-writing check.
- File modes: on systems that have them the roadmap file keeps its own mode, copies are `0600` and the backup folder `0700`.
- A BOM in front of the marker on the first line of the file is allowed.
- A skill eval, `roadmap-restore-needs-yes`. It has not been run against a model yet.

### Changed
- Backups moved: `standardize --write` now writes `<file>.bak-<timestamp>` into `.roadmap-backups/` next to the roadmap file instead of beside it. The folder has a `.gitignore` that holds only `*`, so git never lists or commits anything in it. The folder must be a real folder inside the roadmap file's own folder; a symlink or a file in its place is refused. These are local copies on the same disk, not an off-machine backup, and the script never prunes them.
- A cell that has a backslash directly before a pipe is now written so that this script reads it back exactly (the backslash is doubled), and the reader undoes that: a round trip with the script's own reader. Any other backslash, such as in a Windows path, is written and read as typed. The only text that reads differently from 0.7.0 is an odd run of three or more backslashes right before a pipe in a cell. Nothing is claimed about how a Markdown renderer shows such a cell.
- The new roadmap text is written to `.roadmap-backups/<file>.tmp` instead of `<file>.tmp` beside the file, so nothing that git could list is ever made next to the roadmap; if that name exists the script says another write may be in progress and, if none is, to delete it.
- Every backup name is the real file's name (letter case, links and short names are resolved), so one roadmap has one set of copies. A file that sits inside a `.roadmap-backups` folder is refused (exit 2), and so is a file name with a colon on Windows.
- A `.gitignore` in the backup folder that is a folder or a link is refused (exit 1, nothing written); one whose content is not exactly `*` is left as it is and the script prints a warning that git may list the backups.
- `restore` exits 1, not 2, when the backup folder cannot be used, like `set` and `standardize`. `standardize --write` and `restore --write` print the "first version kept" line when they make the `.original`, as `set` does.
- The guard version is 0.7.1, kept equal to the plugin version. No guard rule changed.

### Added

  - the builder and checker use `git` only to read, inspect and stage, and `gh` only to read (`git` and `gh` are allowlists: anything not listed is denied, with a reason that says what is allowed); they can't set a request method other than GET, a body, a form or an upload (including attached short options such as `-d@file`) with `curl`, `wget` or `Invoke-WebRequest`, and can't `git fetch` with `--force` or a `+` refspec, can't publish or deploy (including task runners given a deploy, release or publish target such as `turbo run deploy` and `run-s deploy`, `node node_modules/.bin/wrangler deploy`, `wrangler workflows trigger`, `npm version patch`, `jsr publish` and `goreleaser release`), and use Bash rather than PowerShell or cmd;

  - every role is denied environment that changes git or skips hooks or moves git's config (assignments, `export` and the targets of `read`, `printf -v`, `mapfile` and `getopts` are checked for any `GIT_*` variable, `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, `HOMEDRIVE`, `HOMEPATH`, `HUSKY` and similar) and git's `--git-dir` and `--work-tree`, any word with a `.git` or `.husky` folder in it, or naming git's global or system config file (`.gitconfig`, `.config/git/config`, `etc/gitconfig`, `ProgramData/Git/config`) (and a Write, Edit or NotebookEdit to one), syntax the guard can't read (`$'..'` quoting, brace expansion, function definitions, a Windows path with single backslashes outside quotes), `eval`, `Invoke-Expression`, `trap`, `alias`, `hash`, `coproc` style launchers, a shell that reads commands from stdin (`... | bash`, `bash <<< '...'`, a bare `bash`, `bash -s`, also behind `nohup`, `timeout`, `sudo` and similar), `gh auth status -t` and `--show-token`, and any command over 32768 characters;
  - model-scout can write only `PHASES.md` in the project folder (the hook input's working folder), never inside a `.claude` folder.

  It restricts only a call made inside one of the four agents (the plugin names `phased-shipping:builder` and so on, or `--agent <role>` in a personal copy), so the main session and other agents are never affected, and it does not load its rules for them. It splits commands before matching, so `cd x && git push`, `bash -c "git push"`, `npx wrangler@latest deploy` and `echo $(git push)` are all seen; PowerShell and cmd are not parsed for the agents (every role is refused them), though `hooks/lib/shell.mjs` still reads their text for other hook plugins that copy it. Inside a known agent it fails closed: unreadable input, a missing or half-copied rules file and any error deny. With no readable role and unreadable input it allows. It reads only the call, writes nothing and makes no network calls. It over-denies on purpose: a false deny costs one retry. It is an extra layer on top of the agents' own rules and `run`'s gates, and it is not a sandbox: a script an agent writes and runs (`bash script.sh`, `source script.sh`), a variable that holds a program name, a flag hidden in a variable for `gh api`, `curl` and the builder's deploy tools, and a `.git` path built from a variable, glob or command substitution (for example `"$(git rev-parse --git-path hooks)/pre-commit"`), or text piped into `xargs` for the builder and checker (`echo deploy | xargs npx wrangler`), stay open. The lists are an extra layer, not a complete list of what could go wrong.

The script refuses a Claude home path containing `$`, a backtick or a double quote, and stops, naming the file, if an agent copy comes out without its hooks block.
