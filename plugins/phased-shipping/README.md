# phased-shipping

A Claude Code plugin for shipping work in small phases, with one deploy per phase. Each step runs on the cheapest model and effort that can do it well.

## What you get

| Component | Model, effort | What it does |
|---|---|---|
| `/phased-shipping:plan` (skill) | opus, high | Sizes the work: trivial (skip), small (one phase) or large (roadmap). The roadmap has priority, urgency, a calibrated estimate, and model and effort per task type (plan, build, tests, browser checks, review, commit, deploy). It writes one detailed phase plan at a time. Claude can invoke it on its own. |
| `/phased-shipping:run` (skill) | sonnet, medium | Runs one phase: gates, a baseline, the build, checks against the baseline, and a preview. It stops for your approval before anything is committed, deployed or pushed, then rolls back automatically if the prod check fails. It records the outcome to the phase history. Manual only. |
| `/phased-shipping:roadmap` (skill) | sonnet, low | Checks a project's roadmap file against the roadmap format, standardizes an older roadmap into it, adopts a project's existing plan files into a roadmap, or puts a kept copy back. `check` only reads. `standardize`, `adopt` and `restore` print a diff or a proposed table and write only after you say yes, with copies kept first in `.roadmap-backups/` next to the file. Manual only. |
| `/phased-shipping:onboard` (skill) | sonnet, low | First run in a project. It lists the files it would read, reads nothing until you confirm, saves a survey of the project's commands, CI and conventions in `.phased-shipping/` inside the project, says whether the project already has a roadmap table or plan files, and points to `standardize`, `adopt` or a fresh roadmap. Recommended, never forced. Manual only. |
| `/phased-shipping:dashboard` (skill) | sonnet, low | Turns the dashboard data on or off, lists the projects it follows, and merges roadmaps, plan timestamps, phase history and running sessions into one local JSON. Its `page` mode builds the dashboard page from it (the page script `page.mjs` with its style, script and fonts in `assets/`). Off until you say yes. Manual only. |
| `model-scout` (agent) | sonnet, medium | Combines three sources: which models you can use, current official guidance, and how each model actually did in your phase history. Refreshes on first use, a provider change, a retirement within 60 days, or after 30 days. |
| `builder` (agent) | per phase plan | Implements one approved plan. Never commits or deploys. |
| `checker` (agent) | haiku, low | Runs typecheck, lint, tests, build and browser checks, first as a baseline and then compared against it. Only new failures block. Results come from exit codes. |
| `shipper` (agent) | haiku, low | Commits, deploys, runs the prod check and rolls back on failure, but only actions marked `APPROVED:`. It scans the staged diff for secrets and respects no-deploy windows. |

State lives in two places:
- **`PHASES.md`** at your repo root: the roadmap, the Model check, status and ids. A new session picks up from it instead of exploring the code again.
- **The phase history** (`history.jsonl` in the plugin's data directory, shared by all your projects). Every shipped phase records estimate against actual agent time (approval waits excluded), the build model and effort, fix rounds, prod first-pass, rollbacks and the agent tokens used. `plan` turns this into an estimate multiplier per kind of work, and into model picks backed by your own results.

## How the model is enforced

- **Planning** is pinned to `opus` at high effort through the skill's frontmatter, so it can't run on a weak model. If your account falls back to another model, it stops and says so.
- **Building** runs on the model and effort the phase plan names. `run` launches the builder with those values per call.
- **Run's gates** refuse to build in these cases:
  - there is no plan;
  - the Model check is stale;
  - the plan's model isn't available to you;
  - the plan puts risky core logic below the mid tier, or a security review below the strongest tier.
- **The override gate** also stops `run` when `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is set, or when `CLAUDE_CODE_EFFORT_LEVEL` differs from the plan's build effort, because either one silently changes what the plan promised. You can say "proceed anyway", and the plan records it. The gate checks environment variables and the settings files the session can read, so a managed-settings override it can't read won't be caught. A separate version check warns, without stopping, when Claude Code is older than v2.1.292.
- **Checks and shipping** always use the cheap agents.

No hook can enforce the model, because tool-call hooks never see the model name. The guard below, a different hook, does a different job: it limits what the plugin's agents may run.

## The guard

The guard is an extra layer. The agents' own rules and `run`'s gates are still the controls, and the guard is never the only one.

It is a `PreToolUse` hook (`hooks/guard.mjs`) that looks at every Bash, PowerShell, Write, Edit and NotebookEdit call. It only restricts a call made inside one of the four agents; with no agent it allows at once, so your main session and every other agent are never restricted. When it denies, it names the rule and what is allowed, and the agent gets one clear reason to report instead of working around it.

`git` and `gh` are **allowlists** by role. Each agent gets the subcommands its job needs, and everything else is denied, including aliases, subcommands the guard has never heard of and the write forms of allowed ones. Over-denying costs the agent one retry; letting something through is the failure that matters, so when a form is unclear the guard denies it.

| Agent | The guard allows | Everything else is denied, in particular |
|---|---|---|
| `builder`, `checker` | `git`: status, diff, log, show, blame, grep, ls-files, ls-tree, ls-remote, rev-parse, rev-list, describe, name-rev, merge-base, show-ref, cat-file, shortlog, diff-tree, check-ignore, fetch (no `--force`, no `+` refspec), add, restore, rm, mv, apply; `remote` (-v, show, get-url), `stash` (push, list, show, pop), `branch` and `tag` (list forms only), `config` (get and list only), `reflog` (show, list), `checkout` and `switch` (no force, no orphan), `clean` (dry run only). `gh`: view, list, status, diff, checks, watch, search and download on pr, issue, run, release, repo, workflow, gist, label and project; `auth status`; `api` with GET only | `git` commit, push, pull, merge, rebase, cherry-pick, revert, reset, am, notes, update-ref, aliases, force forms and unknown subcommands; `git -c` for any key that can run a program; `gh` writes of every kind, `gh alias`, `gh extension`, `gh auth token`; `curl`, `wget` and `Invoke-WebRequest` calls with a method other than GET, a body, a form or an upload, including attached short options such as `-d@file`; publishing and deploying (`npm publish`, `npm version patch`, `docker push`, `wrangler deploy`, `wrangler workflows trigger`, `terraform apply`, `kubectl apply`, `goreleaser release`, `jsr publish`, task runners given a deploy, release or publish target such as `turbo run deploy`, `nx run app:deploy`, `lerna run deploy`, `run-s deploy`, `node node_modules/.bin/wrangler deploy` and the long list in `hooks/guard-rules.mjs`); `powershell`, `pwsh`, `cmd` and the PowerShell tool (every role uses Bash) |
| `shipper` | `git`: add, commit, push, revert, status, diff, log, show, rev-parse, rev-list, describe, fetch (no `--force`, no `+` refspec), ls-remote, cat-file, `remote` (-v, show, get-url), `branch` (list), `tag` (create or list), `config` (get and list). `gh`: run (watch, view, list), issue (view, list, close, reopen), pr (view, list, checks), release (view, list), repo view, workflow (view, list), auth status, api with GET | force-pushes (every spelling, including short prefixes like `--force-w`, `--mirr`, `--del`), `--mirror`, `--prune`, deleting a remote ref; skipping hooks or signing; `commit --amend`, `rebase`, `reset`, `clean`, branch delete, stash, pull; every other `gh` command, including delete, merge, release create and `gh api` writes; `curl`, `wget` and `Invoke-WebRequest` calls with a method other than GET, a body, a form or an upload, including attached short options such as `-d@file`; `xargs`; `powershell`, `pwsh`, `cmd` and the PowerShell tool (use Bash); any variable, `$(...)` or backtick in an argument of `git push`, `commit`, `revert` or `tag`, because it could hide `--force`, `--no-verify` or `+main` (the one exception is the text after `-m`, `--message`, `-F` or `--file`, so `git commit -F "$TEMP/msg.txt"` works) |
| every role | | Environment that changes git or skips hooks or moves git's config (assignments, `export` and the targets of `read`, `printf -v`, `mapfile` and `getopts` are checked for any `GIT_*` variable, `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, `HOMEDRIVE`, `HOMEPATH`, `HUSKY*`, `SKIP`, `LEFTHOOK*`, `BASH_ENV` and a few more), and git's `--git-dir` and `--work-tree`; any word with a `.git` or `.husky` folder in it, or naming git's global or system config file (`.gitconfig`, `.config/git/config`, `etc/gitconfig`, `ProgramData/Git/config`) (the shell, and the Write, Edit and NotebookEdit tools): that is where hooks and config live (`.gitignore`, `.github` and `.gitattributes` are fine); syntax the guard can't read (`$'..'` quoting, `{a,b}` brace expansion, function definitions, a Windows path with single backslashes outside quotes); `eval`, `Invoke-Expression`, `Start-Process`, `Start-Job`, `Invoke-Command`, `trap`, `alias`, `hash`, `coproc`, `enable`, `shopt -s expand_aliases`, a shell that reads its commands from stdin (`echo 'git push -f' \| bash`, `bash <<< '...'`, a bare `bash`, `bash -s`) and launchers it can't follow (`busybox`, `su`, `script`, `parallel`, `flock`, `strace` and similar); `gh auth status -t` and `--show-token` (they print the token); any command over 32768 characters ("command too long to check") |
| `builder` only | | writing `PHASES.md`, or a `phase-*.md` file inside a folder named `phases`, with the Write, Edit and NotebookEdit tools, or from the shell in the common write forms (`>` and `>>`, also glued to a word, `tee`, `sed -i`, `mv` or `cp` onto it, `Set-Content`, `Out-File`, `git checkout` and `git restore` onto it); writing the approval records (`previews/<key>.planned.json`, `.previewed.json`) or anything under `.claude/phased-shipping/`, `.claude/skills/ps-run`, `.claude/skills/ps-plan` or `.claude/agents/ps-*` the same ways; see How approval works |
| `model-scout` | writing `PHASES.md` in the project folder (the hook input's `cwd`) | writing any other file, any path with a `.claude` folder in it, any write when `cwd` is missing; it has no shell |

The guard splits each command before matching: `cd x && git push`, `git -C ../repo push`, `FOO=1 git push`, `/usr/bin/git push`, `bash -c "git push"`, `bash -c -- "git push"`, `env -S "git push"`, `npx wrangler@latest deploy`, `pnpm -C app exec wrangler deploy`, `powershell -Command "git push"`, `cmd //c "git push"`, `echo $(git push)` and `sudo git push` are all seen. PowerShell and cmd are not parsed for the agents: all three roles are refused `powershell`, `pwsh`, `cmd` and the PowerShell tool outright (their workflows use Bash), because their quoting, aliases, assignment and script-block syntax kept hiding commands. `hooks/lib/shell.mjs` still reads PowerShell and cmd text (backticks, curly quotes, Unicode spaces, `<# #>` comments, `$x = git ...` assignments, every `{ }` block, cmd's `call`, `@` and `if`) for other hook plugins that copy the file. git accepts any unique prefix of a long option, so the guard treats `--x` as a flag whenever the flag's name starts with `x`. The exact lists are in `hooks/guard-rules.mjs`.

**It says when it isn't active.** Every `run` starts the checker with a self-test probe, `echo phased-shipping-guard-probe`. When the guard is on, it blocks the probe ("phased-shipping guard is active for checker"), and nothing runs. If the probe runs, the guard isn't active in that session, and the preview says so. This never stops the phase. The result is recorded as `guard` in the phase history, and `history.mjs stats` prints how many phases had it active.

**Fail-closed rule.** The guard works out the role first (from `agent_type`, or from `--agent` in a personal copy) and only then loads its rules. Inside a known agent, if it can't judge a call, it denies it: input it can't read, a missing or half-copied rules file, an error while judging, a command that is too long, nesting that is too deep. With `--agent <role>`, unreadable input is denied too, because the role is known from the argument. If there is no role and the input can't be read, it can't tell whose call it is, so it allows.

**Plugin install and personal copies.** A plugin install wires the guard through `hooks/hooks.json`, matched on the agent type (`phased-shipping:builder` and the other three, nothing else). Plugin agents ignore a `hooks` field in their own files, so the plugin's agent files have none. `sync-personal.mjs` instead copies the hook scripts to `~/.claude/phased-shipping/hooks/` and adds a `hooks:` block to each generated `ps-*` agent file that runs the guard with that agent's name (`--agent builder` and so on); the `ps-*` names are not roles, so a personal copy relies on that argument. It edits no settings file. The personal block also sets `onFailure: block`, so if the hook can't run (node missing, the script gone), the call is blocked instead of going ahead. That needs Claude Code v2.1.295 or later; on an older version the key is most likely ignored (what an older version does with an unknown key is undocumented), so the personal-copy hook then fails open like the plugin's. The plugin's `hooks.json` does not set it: a missing `node` would then block your main session too, so there a hook that can't start lets the call through. The script refuses to install when the Claude home path contains a `$`, a backtick or a double quote, because the hook command is shell text.

## How approval works

`approve` doesn't take the commands from your memory of the preview. At the preview, `run` shows the plan's deploy, prod-check and rollback commands verbatim, with a `Commands hash` of 12 hex characters (the SHA-256 of the plan's `## Commands` section, after CRLF, trailing spaces and trailing blank lines are normalized), and records that hash and the text in the plugin's data folder (`~/.claude/phased-shipping/previews/` for personal copies). The script prints the recorded section, and the preview shows that printed text. On `approve` and on `push`, `run` checks the plan against that record before it briefs the shipper, and the check prints the section again. The shipper brief takes the deploy, prod-check and rollback commands only from that printed, recorded section, copied verbatim, never from a fresh read of the plan, the preview turn or memory, so what was hashed, shown and run are the same text. A plan with two headings that look like "Commands", or one that isn't exactly `## Commands`, is refused as ambiguous. If a command changed in between (an edit by you or another session, a `git pull`, a builder that touched the plan), it stops, shows the diff and tells you to run `/phased-shipping:run N` again to preview the current commands. There is no "re-preview now" shortcut: a fresh preview turn is the point. With no record at all, it stops and asks for a preview first. The shipper repeats the hash in its report, so the phase report shows which commands were approved.

The plan skill makes a first record when it writes the plan (`planned`). If the commands changed between planning and the preview, the preview shows the diff as a warning, not a stop, because you may have edited the plan on purpose. A plan made elsewhere or before 0.5.0 has no planning record, and the preview says so. The `Commands hash` line in the plan file is a convenience that anyone can edit; the record in the data folder is the one that counts. As a second layer, the guard denies the builder writes to `PHASES.md` and `phase-*.md` files in a `phases` folder (also `git checkout` and `git restore` onto them, `cp`, `mv`, `install` and `rsync` into them, `git apply` and `git mv`), and to what the binding trusts: the approval records (`previews/<key>.planned.json` and `.previewed.json`), the personal copies' data folder, skills and agents (`.claude/phased-shipping/`, `.claude/skills/ps-run` and `ps-plan`, `.claude/agents/ps-*`), and the installed plugin folders for phased-shipping (`.claude/plugins/cache`, `marketplaces` and `data`, any path there with `phased-shipping` in it), so the builder can't change the commands, the records or the installed script, hooks and skills before the preview. It also denies the builder running `commands-hash.mjs` with `--record` (only the run skill records approval fingerprints; `--check` and `--short` stay allowed) and `node -e` text that writes into a `previews` folder. Reading all of these stays allowed, and `git restore --staged` alone (it only unstages) is allowed.

This protects against accidental and model-made drift. It does not protect against a malicious local process that can rewrite both the plan and the record. The limits:
- The builder can still forge a record by running the script from its own `node -e` or from a script file it writes: the guard denies the plain forms, not every way to run node.
- The builder's shell rules are best effort. They read literal paths in the common write forms (dot segments, doubled slashes and a trailing `/.` are resolved), not a path built from a variable, a glob, or a `cd` followed by a bare file name, nor `git stash pop`, a whole-folder `git checkout`, subshell or brace-group redirects, `>|`, other in-place editors, or scripts. They also deny a quoted literal such as `echo "a>PHASES.md"`.
- The record key is path-based (the plan's real path, with symlinks and short Windows names resolved, lower-cased). A relative and an absolute path to the same file share a key, but a different spelling that resolves elsewhere (a copy, another checkout) is another plan and may need a new preview.
- A `previewed` record is not used up: an `approve` in a later session still matches an old preview of an unchanged plan. The commands are unchanged, so this is accepted.
- A fix-forward round that changes the plan's commands needs a new preview (Preview steps 1 and 2 again, then end the turn) before the fresh `approve`.
- It needs `node` and, unlike the guard, doesn't depend on hooks, so it works where an organization policy turns hooks off.

## Requirements

- Claude Code v2.1.292 or later (per-call effort; older versions run subagents at their file's effort).
- For the guard: `node` on your PATH (the hook is a node script), and, for the personal copies' `onFailure: block`, Claude Code v2.1.295 or later.

## The roadmap format

A project keeps its roadmap as Markdown tables in `PHASES.md`. The roadmap format makes that table the same everywhere, so one reader can tell what is planned, in progress, shipped or parked. The full description is in [references/format.md](skills/roadmap/references/format.md); in short:

- A table is a **standard** table when the line above its header is exactly `<!-- phased-shipping:roadmap v1 -->`. It needs the columns `#`, `Phase` and `Status`; `Status` is one of `planned`, `in progress`, `shipped` or `parked`. Other known columns are optional, and a column the reader doesn't know is ignored and kept as it is.
- A table without the marker is **legacy**. It is read as well as possible and reported with a notice, never rejected.
- `/phased-shipping:roadmap check` lists the problems, with line numbers, and edits nothing. `/phased-shipping:roadmap standardize` turns a legacy table into a standard one: it shows what would change, asks you, keeps your first version and a dated copy in `.roadmap-backups/` next to the file and only then writes. A Status it can't place is never guessed: you choose. `/phased-shipping:roadmap restore` lists the kept copies, shows what putting one back would change, asks you, saves the current file first and only then restores.
- `/phased-shipping:roadmap adopt` reads a project's existing plan files (`phase-*.md`) and proposes roadmap rows for what those files prove: the id and title from the first heading, and a status only from the `**Timestamps:**` line. A plan file with no real timestamps is listed as undecided and left out unless you give it a status. It writes only after you say yes, appends a new table (never overwrites a roadmap) and keeps the same copies as `standardize`.
- `plan` writes the marker and runs `check` on the roadmap it writes. `run` marks the phase `in progress` and, at close, `shipped` with the commit and the hours, one row at a time, on a standard table only. A legacy roadmap is left alone, and `run` says so once.
- The reader is one script, `roadmap.mjs`, with no dependencies. Other tools can import its `parseRoadmap` rather than write a parser.

## Onboarding

Installing the plugin runs nothing. The first run in a project is `/phased-shipping:onboard`: recommended, never forced. The plan skill offers it once when the project has no saved survey, and remembers a no.

1. **List.** `survey.mjs list` prints the files it intends to read (category, relative path, size) and reads nothing but folder entries and sizes.
2. **Confirm.** You can remove files. Nothing is read until you confirm. `list` also prints a digest (a hash of the sorted paths and sizes); `run --all-listed` needs it as `--list-digest` and refuses, reading nothing, if the project's files differ from the list you saw. A `--confirm` file never widens the list: entries that are not on the current list are only counted, never read and never printed.
3. **Survey.** `survey.mjs run` reads only the confirmed files and saves `.phased-shipping/survey.json` inside the project. The summary holds exactly this: the stack; each script's name (test, build, lint, deploy) with the command that invokes it (`npm run <name>`, `make <name>`, or the pnpm, yarn or bun form when that lockfile exists) and its source file, never the script's body; for each workflow its file name, job names, action names as `name@ref` without inputs, secret names and a count of run steps (no run line and no word of one); which convention docs exist and a heading count; the top-level key names of deploy configs; the plan folders and roadmap files; and counts of skipped files by reason. Every path in it is relative. It holds no script body, no run line, no line of any file and no absolute path. The names in it (the project name, workflow and job names, a package's name) are text from your files, cleaned to one line of plain text and cut short.
4. **Classify.** `survey.mjs classify` says whether the project has a roadmap table (`table`: standardize it), plan files but no table (`plans`: adopt them), both (standardize first, then adopt the plan files that are not listed) or neither (`none`: the plan skill writes a fresh roadmap).
5. **Choose.** You choose the path and the roadmap skill writes only after its own yes. The first-run checklist shows the survey, the roadmap and the dashboard data (turn it on with `/phased-shipping:dashboard enable`, then open the page with `/phased-shipping:dashboard page`; see Dashboard data and Dashboard page).

There is one mode: `survey.mjs` reads your project files, and the assistant sees the summary the script prints. The skill's instructions tell the assistant to read no other project file and to hand none to another agent; that is an instruction, not a lock (see Limits). The summary goes to your model provider like any other tool output in a Claude Code session. The plan skill uses a saved survey only for proposed commands (baseline, verify, deploy, prod check); you still confirm each one, and nothing runs a command found in the survey.

## Dashboard data

The dashboard is off until you say yes. This section is the data; the page that shows it is described under Dashboard page. Everything stays on your machine, in the plugin's data folder (`~/.claude/phased-shipping` for personal copies). Nothing is sent anywhere.

- **The ask.** The first `/phased-shipping:run` after this version asks once, with AskUserQuestion, whether to turn it on. The default leaves it off, and the answer is remembered. You can change it any time with `/phased-shipping:dashboard enable` or `disable`. The script enforces this, not only the skill's text: while it is off, the status calls the run makes write nothing.
- **Status files.** While it is on, a project is added to a local list when a run starts in it (with the history label the run records), and the run writes one small status file per phase at each step: baseline, build, a check-in, compare, review, approve (waiting for your approval), ship and prod check. Each call is a no-op when the dashboard is off, and a failed call never fails a gate.
- **The list.** `/phased-shipping:dashboard list` shows the projects (id, name, labels, roadmap files). `register` adds one by hand (the dashboard must be on), `unregister` removes one (it also works while the dashboard is off; while it is on, the page is rebuilt without that project). A moved or deleted folder is shown as `not found` and is never removed by the tool. **The repository is the project:** the run names the folder that holds `PHASES.md`, and the project is the repository around it, the nearest folder up to 40 levels above (itself first) that has a `.git` entry, found by its name only (never opened or followed) and ignored at your home folder or above; where the system has user ids, a `.git` that another user owns is not trusted (the climb stops and your folder is the project), and a folder inside `.git`, `node_modules` or `.roadmap-backups` is refused. So a roadmap kept in `docs/roadmap` is one project with its repository, with `docs/roadmap/PHASES.md` added to its roadmaps, and two roadmap folders in one repository are one project with two roadmaps, whose sessions are kept per roadmap and phase. When a roadmap is not added (too deep, a folder name with a character that is not allowed, or ten roadmaps already) the command says why in one extra line; a run in such a folder still keeps its own session file, which has no roadmap, title or estimate of its own and never shares a file with another roadmap. With no repository the folder itself is the project, as before; entries already in the list are never migrated (a command that does not change the list leaves the file as it is, and a stored roadmap that is not a usable path is ignored when the list is read and left out when it is next written).
- **One JSON.** `/phased-shipping:dashboard collect` merges the listed projects' roadmaps, the timestamps in their plan files, their phase history (joined only by the labels stored with the project, never by folder name) and the running sessions into one JSON, in [references/status.md](skills/dashboard/references/status.md). A session shows as `Working`, `Waiting for you`, `Done` or `Idle` (no update for 180 minutes), a working session with no update for 90 minutes is flagged, and a project with two open sessions gets a warning.
- **Limits.** Only the roadmap files listed for a project, and the plan files they name, are read, and only when their real path is inside the project, they are regular files (never a link or a hard link) and they are at most 256 KB. There is one status file per project, roadmap and phase, so two sessions on the same phase of the same roadmap share it, and the same phase id in two roadmaps of one repository does not. A crashed run leaves its file; it shows as `Idle`, and `clear` or `unregister` is yours to use. The thresholds (90 and 180 minutes) are in `dashboard.json` and can be edited.

## Dashboard page

`/phased-shipping:dashboard page` builds one local HTML file, `dashboard.html` in the data folder, and tells you where it is; open it in a browser. While the dashboard is on, `status.mjs` also rebuilds the page after each `set`, `clear` or `unregister`, so it follows the run and an unregistered project leaves it. While it is off, `status.mjs` builds nothing, and `disable` leaves the page as it was last written. The `page` command itself is yours and builds the page whether the dashboard is on or off. A page that cannot be built prints one line, `page not rebuilt (<reason>)`, and the status call still exits 0.

- **What each level shows.** A project is a closed row with a one-line summary: its standard roadmaps, phases shipped, sessions working, waiting and idle, archived sessions, and the estimate and time worked of the active ones. A project with a working or waiting session starts open. Inside it: the sessions, each with the eight gates of a phase (Baseline to Prod check), its step, round, time on the step, last update and worked time against the estimate; a Roadmap table; an Estimate against actual table from the history log (the actual hours come from timestamps and include any time the run waited for you; a shipped row of a standard roadmap with an Actual and no history record is added); and an Archived sessions list. Archived means done and more than 7 days since the last update; it is this tool's word and not Claude Code's own archive, which the tool cannot read.
- **Only standardized roadmaps.** Only standardized roadmaps are drawn: a roadmap file counts when it has at least one table and every table has the `<!-- phased-shipping:roadmap v1 -->` marker line. A file that does not (a legacy table, a file with two tables of which one has no marker, a file with no table) is not drawn and not counted; the project shows one note naming it (at most 10 names), `N roadmap files not standardized: <names> (not drawn). Standardize them with the roadmap skill, mode standardize.`, and its row says `(N not standardized)` after the number of roadmaps. A project with no standard file shows that note, the line `No standardized roadmap yet.` in its Roadmap part and no roadmap bar. The Estimate against actual part still shows from the history; a phase that is in no standard roadmap shows its id alone. To fix it, run the roadmap skill in standardize mode on each named file. The merged JSON still holds the data of those files (`roadmaps[].standard` says which are standard, and the summary counts standard files only, with `legacyFiles` and `legacyNames`).
- **The look.** The in-progress colour is the logo's salmon with its diagonal hatch (on the dark page `#FFB28F`; on the light page the light logo's `#B33A0B`, because the pale one is 1.6:1 there): it is the running gate of a session and the in-progress mark of a roadmap row. While a session is working the hatch drifts slowly and the header rule at the top of the sheet is a salmon stripe that flows slowly; with nothing working that rule is the same stripe, still. The drift moves a clipped layer by transform, which a browser can animate off its main thread, and a page with more than 25 moving things keeps only the header rule and the running gates moving. The salmon is used only on borders, strokes and hatching, never on text or a fill, and every state keeps its word and its shape. "Waiting for you" keeps its square stamp and a different accent (a rose on the dark page, a crimson on the light page). The motion is CSS only, off when your browser asks for reduced motion and in print, and the Pause button stops it too.
- **The roadmap bar.** Each project row has a slim bar of its standard roadmap phases, as the logo's three squares: shipped (filled), in progress (hatched salmon, moving), planned (outlined), in proportion to the counts, with a label such as `3 shipped, 1 in progress, 3 planned`; parked phases are named in the label and not drawn; with no standard roadmap file there is no bar.
- **The title block.** The foot of the sheet shows real figures as written: when the page was written (UTC), the number of projects, phases shipped of all phases of the standard roadmaps (`23 of 72`), sessions active and waiting for you (`2 active, 1 waiting`, only sessions of listed projects), archived sessions and the source. The page does not trust the figures it is given: a summary number that is not a whole number of zero or more is counted again from the rows it draws, and a written time that is missing or unusable shows as `unknown`.
- **The loop arrows.** A run that goes back (Compare back to Build, or Prod check back to Build after a rollback) is drawn as a right-angled arrow under the gates, from the gate it left to the gate it returned to, with its count (`x N`) and the two step names as text. A gate entered again says `round N`. Only the loop that is active right now moves; every other arrow is still, and none moves in print or when your browser asks for reduced motion. The animation restarts at each reload. The loops come from the trail in the session file (an optional list of the last 40 changes of step or state).
- **Refresh.** The page reloads itself every 10 seconds (`page 30` makes it 30; the range is 5 to 300), holds while you select text or hover a cut-off title, and has a Pause button. Its clocks keep running between reloads, and a banner appears when the page has not been rewritten for 90 minutes. The refresh, the Pause button, the clocks and the 90-minute stale banner need JavaScript; without it the page shows the times as written and a notice, and the refresh text and Pause button are hidden.
- **Fonts.** The page carries two embedded fonts, PW Sans and PW Mono: subsets of IBM Plex Sans and IBM Plex Mono under the SIL Open Font License 1.1, given new names because the licence reserves the name "Plex". The family names are PW Sans and PW Mono and the PostScript names start with `PWSans-` and `PWMono-`; only the copyright and licence records of each font keep the Plex notice, as the licence requires. The licence text is the file `skills/dashboard/assets/OFL.txt`, and the page names it in its first comment. `--no-fonts` leaves the fonts out and the page uses your system fonts.
- **A big page.** The page has a soft limit of 256 KB and a hard limit of 1 MB. Over the soft limit it is made smaller instead of being left stale: the Roadmap and Estimate against actual parts of projects that have no working or waiting session are replaced by one note line ("left out to keep the page small: N rows; the dashboard JSON still has them"), the project with the most to save first, until the page is under 256 KB or nothing is left to drop; if it is still over, the tables of the projects with a running session go the same way. A project's row, its sessions (a waiting one always) and its archived sessions always stay, and the page says in a visible line when it has left something out. A page that is still over the hard limit of 1 MB with every table left out is not written at all (`page not rebuilt (page too large)`).
- **No network.** The page's policy is `default-src 'none'` with a hash of its one script, it has no outward link, and its script makes no request. It holds no JSON, and no path the tool builds appears in it; text copied from your files is shown as written (known path forms of this machine are replaced), so do not put paths in plan text. Every text from your files is cleaned, escaped and treated as plain text. These properties are checked by the tests against the page's text and the script's source; nobody has run the page in a real browser as part of the tests.
- **A narrow screen.** The phase flow keeps its size and scrolls sideways (a hint says so) instead of wrapping, so a loop arrow always joins the two gates it names.

## What it touches

This is everything the plugin reads, writes and runs, taken from its skills, agents and script.

**Files it reads**
- Your project: the files named in the phase plan, plus the manifest, README and source files the planner needs to size the work.
- Settings and environment: the `model`, `availableModels` and `effortLevel` keys of your Claude Code settings files, any model convention in `CLAUDE.md`, and the values of only these environment variables: `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL*`, `CLAUDE_CODE_EFFORT_LEVEL` and `CLAUDE_CODE_USE_*`. It never prints the rest of the environment or of those files.
- The phase history file, and the approval records in the data folder (see How approval works).
- The roadmap file (`PHASES.md`), through `roadmap.mjs`, for `check`, `read`, and the plan and run skills. It prints only the file's base name. `restore` also lists and reads the copies in `.roadmap-backups/` next to it (and any `<file>.bak-<timestamp>` copy an earlier version left beside the file).
- **The survey** (`survey.mjs`, run by the onboard skill) reads only these files, and only after you confirm the list: `README*`, `CONTRIBUTING*`, `CLAUDE.md` and `AGENTS.md` in the project root, `docs/*.md` and `docs/*/*.md` (a heading count is kept, no text); `package.json` (name and script names, never a script body), `pyproject.toml` (name and script names), `Makefile` (target names, never a command), `Cargo.toml` and `go.mod` (name); `.github/workflows/*.yml` and `*.yaml` (job names, action names as `name@ref` without inputs, secret names and a count of run steps; never a `run:` line or a word of one); `wrangler.toml`, `wrangler.json`, `wrangler.jsonc`, `netlify.toml`, `vercel.json`, `fly.toml` and `Dockerfile` (top-level keys only, no value); and `phase-*.md` and `PHASES.md` under `docs/`, `.plans/`, `plans/` and `phases/` (the first heading and the roadmap tables). It **never** opens source code, `.env*`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`, `.npmrc`, `.pypirc`, `.netrc`, cloud and kube credential files, `*.sqlite`, `*.db`, dumps, anything inside `.git`, `node_modules` or build output, lockfiles (their names only), files over 256 KB, binary files or hard-linked files, and it never follows a symbolic link or junction (a link inside `docs/` or a plan folder is counted and reported as skipped). A file whose text matches a known secret shape (token and key formats, private keys, passwords, and a secret-looking name with a value, checked as written, with escapes decoded and as parsed JSON values) is skipped whole and counted. As a last check the finished survey and every printed line are scanned again, and a match exits 1 with nothing saved and nothing printed. The patterns catch the shapes they know, not every secret. Caps: 200 files, 64 KB of text per file, 400 KB for the survey. A locked file is skipped once and never retried. `list` reads folder entries and sizes only. The script makes no network calls and sends nothing anywhere; it prints no absolute path.
- **The dashboard data** (`status.mjs` and `collect.mjs`, run by the run and dashboard skills): the three files below in the data folder and `history.jsonl`; and, for each project on the list, only the roadmap files listed for it and the plan files those roadmaps name. A file is read only when its real path is inside the project, it is a regular file (not a link, not a hard link) and it is at most 256 KB; the others are reported by base name and reason. Each file is opened once and checked through the open file (a regular file with one name, at most 256 KB) before it is read. A plan file under a `.git`, `node_modules` or `.roadmap-backups` folder is refused. Nothing else in a project is opened. The merged JSON holds relative paths and base names only. No path the tool builds appears in it, and it holds no line of a file beyond the table cells and timestamps it was built from. Text copied from your files is shown as written, cleaned to one line of plain text and cut short, with the known forms of this machine's project, data and home folder paths (and of `<drive>:\Users\<name>`, `/c/Users/<name>`, `/Users/<name>` and `/home/<name>`) replaced by `[path]`; other spellings of a path may remain, so don't put a path in plan text. Every string in it is untrusted plain text, and `<`, `>` and `&` are written as `\u` escapes so the JSON is safe to inline in a page. It makes no network calls.
- **The dashboard page** (`page.mjs` and the files in `assets/`, run by the dashboard skill and, after a `set`, `clear` or `unregister`, by `status.mjs`): reads the same data as the merged JSON, through the collect script, and the four files of `assets/` that make the page (`page.css`, `client.js` and the two fonts, `pw-sans.woff2` and `pw-mono.woff2`). It opens no other file. No path the tool builds appears in the page (text copied from your files is shown as written, and known path forms of this machine are replaced, so do not put paths in plan text), and it holds no line of a file beyond the text the merged JSON holds. It makes no network calls, and the page makes no network request.
- **The guard hook** reads nothing but the call it is handed (the tool name, the command or the file path, the working folder and the agent type). It runs on every Bash, PowerShell, Write, Edit and NotebookEdit call in any session where the plugin is enabled, your main session included, where it allows at once. Each call starts one node process. Measured on the allow path (a main-session payload, 30 runs, on a busy Windows laptop): median 1341 ms, p95 2667 ms. An empty node script on the same laptop took a median of 1298 ms, so about 40 ms is the guard's own work and the rest is node starting, which varies a lot by machine. Expect a delay on every Bash, PowerShell, Write and Edit call, in every session where the plugin is enabled. It writes no files and makes no network calls.

**Files it writes**
- `PHASES.md` at your repo root (roadmap, Model check, status).
- The plan folder, one file per phase (default `docs/phases/`): the plan, its timestamps and its phase report.
- The checker's baseline file and its logs or screenshots, at the paths the brief names.
- The phase history, `history.jsonl`: `${CLAUDE_PLUGIN_DATA}/history.jsonl` for a plugin install, `~/.claude/phased-shipping/history.jsonl` for personal copies. A phase record is one line with the estimate, agent time, build model and effort, fix rounds, prod outcome and, from 0.3.0, the agent tokens per phase. It holds no code and no project text beyond the project name.
- A temporary JSON file that holds the record while the history script appends it.
- The roadmap file, in three ways, always through a temp file in the backup folder (`.roadmap-backups/<file>.tmp`) and a rename. The file keeps its own permissions. `standardize --write` rewrites the tables you chose, and `restore --write` puts a kept copy back, both only after you say yes. `set` rewrites one row of one standard table.
- The backup folder, `.roadmap-backups/`, next to the roadmap file. It holds copies of your roadmap text, so don't share it. Its `.gitignore` is a single line, `*`, so git never lists or commits anything in it. Before the first write of any kind the script keeps `<file>.original`: the file as the script first saw it. It is created once, and the script never overwrites, renames or deletes it. `set` also keeps `<file>.prev` (the file as it was before that `set`, replaced each time). `standardize --write` keeps `<file>.bak-<timestamp>`. `restore --write` keeps `<file>.before-restore-<timestamp>`, so a restore can itself be undone. If any of these copies cannot be made, nothing is written to the roadmap and the script exits 1. Each copy is written whole under a temporary name, flushed to disk, and only then given its final name, so a name never holds half a file; where the disk cannot do that (FAT and some network drives), a `<copy>.incomplete` marker is made first and removed last, and a marker left behind makes every later write refuse until you have looked: you compare `<file>.original` with the roadmap, delete it too if it is shorter, different or you are unsure (it is made again from the current roadmap), and then delete the marker. For any other marker you delete the copy it names, then the marker. Copies are readable by you only where the system has file permissions. If the folder's `.gitignore` holds something other than `*`, the script warns and goes on; if it is a folder or a link it refuses. The script never deletes the dated copies; you may delete them, and `.original` is the one to keep, unless an `.incomplete` marker says it may be cut short.
- The survey folder, `.phased-shipping/`, in the root of the project you onboard. It holds `survey.json` (the survey, with relative paths only), `state.json` (the time of the survey, or `{ "declined": "<date>" }` when you said no to onboarding) and a `.gitignore` whose only line is `*`, so git never lists it. The folder is created only if it is a real folder inside the project; if `.phased-shipping` is a file or a link, or its `.gitignore` holds anything but `*`, nothing is written and the script exits 1. Each file is written whole under a temporary name and renamed. Nothing is written without your yes.
- `adopt --write` appends a new standard table under a `## Roadmap` heading at the end of the roadmap file you choose, or creates a new roadmap file (it refuses a name that exists), through the same backups and checks as `standardize`; plan files with no real timestamps are added only with a status you give.
- **The dashboard files**, only after you turn the dashboard on (while it is off, `enable`, `disable`, `asked` and `unregister` are the only `status.mjs` commands that write; the page file below is written by your own `page` command whether it is on or off). All three kinds of file are in the data folder, created on first write, and each is written whole under a temporary name and renamed; the folder and the files must be real (a link, a junction or a hard link makes the script stop and write nothing). `dashboard.json` holds the on or off setting, the date the question was answered and two thresholds. `projects.json` holds, for each listed project (at most 100), an id, its **absolute path**, its folder name, its history labels, its roadmap file names and the date it was added: it is the only file with an absolute path, it stays on this machine, and the scripts never print it except `list --paths` at your request. `sessions/<id>-<tag>+<phase>.json` holds the phase id, its title, the step, the state and two times, at most 16 KB, one file per project, roadmap and phase (it also holds the roadmap's relative path and the step trail; no absolute path). Its status and list files go to the data folder only. `collect --out` writes the one file you name, and is refused inside the data folder; nothing else is written. `--data` must be an absolute path, so an empty or relative one is refused rather than taken as the working folder. Do not point `--data` at a folder tracked by git: `projects.json` holds the absolute paths of your projects.
- **The dashboard page file**, `dashboard.html` in the data folder: written whole under a temporary name and renamed, by `page.mjs` (the explicit `page` command writes it whether the dashboard is on or off, because you run it yourself), and by `status.mjs` after a `set`, `clear` or `unregister` while the dashboard is on (the automatic rebuild never runs while it is off). Over the soft limit of 256 KB it is made smaller (see "A big page" above) and over the hard limit of 1 MB it is not written at all, and the data folder is never created for it. `disable` leaves the page as it was last written. `page.mjs --out <file>` writes the page to another file and is refused inside the data folder (under any name or route: a link, a junction, or a network path such as `\\host\share`, which is refused on every platform) or when the file name has a colon in it (on Windows a colon names a hidden stream and would leave an empty file behind). The session files also gain an optional `trail` (at most 40 entries of step, state and time), written by `set` when the step or the state changes.
- No other file is created. Lines outside the chosen tables are never touched, and `--root` makes the script refuse a file outside the project folder.
- Approval records: `<data folder>/previews/<key>.planned.json` and `<key>.previewed.json`, written by `commands-hash.mjs`. Each holds the hash, the text of the plan's `## Commands` section, the plan path and a timestamp. The script writes nothing else and makes no network calls.
- Personal copies only: the guard scripts under `~/.claude/phased-shipping/hooks/` and the `hooks:` block in each `ps-*` agent file. `sync-personal.mjs` writes both, marks them as generated, and removes only what it marked.
- Your source files, but only through the builder, and only to implement the approved plan.

**Commands it runs**
- Read-only status commands: `git status`, `git diff --stat`, `env` filtered to the variable names above, and `claude --version`.
- The plan's baseline and verify commands, through the checker. The checker never deploys, publishes or pushes, and when the brief has no commands it proposes some and waits for your OK instead of running them.
- The plan's commit, deploy, prod-check and rollback commands, through the shipper, and only after `/phased-shipping:run approve`. A push needs `/phased-shipping:run push` or a plan whose deploy step is the push, and your approval.
- The history script (`history.mjs`), with `stats` and `record`.
- The roadmap script (`roadmap.mjs`), with `read`, `check`, `standardize`, `set`, `restore` and `adopt`. It uses no network.
- The survey script (`survey.mjs`), with `list`, `run`, `show`, `classify`, `decline` and `leftovers`. It uses no network and never runs a command it finds in your files.
- The status script (`status.mjs`), with `state`, `enable`, `disable`, `asked`, `register`, `unregister`, `list`, `set` and `clear`, and the collect script (`collect.mjs`). They use no network and run nothing they find in your files: the one module `collect.mjs` loads (the roadmap reader) is chosen by the script's own folder name, never by a name in a file. The run puts only the phase id, the label (each matching `^[A-Za-z0-9._-]{1,60}$`) and fixed step and state words on a status command line, and never a title or other text from a file.
- The approval script (`commands-hash.mjs`), to hash the plan's commands and record or check them.
- The guard probe, `echo phased-shipping-guard-probe`, through the checker. It prints a word and changes nothing.

**Network**
- `model-scout` runs a web search and fetches up to 3 pages when the Model check refreshes. It treats page content as data.
- The survey script sends nothing anywhere. The script reads your project files; the model sees the summary the script prints (script names and their invoking commands, CI job, action and secret names and a count of run steps, convention-doc flags, plan counts, skipped counts and relative paths). That summary goes to your model provider like any other tool output in a Claude Code session. It holds no script body, no run line and no line of any file; the project name, workflow and job names and a package's name are text from your files (cleaned to one line of plain text and cut short), and they are in it.
- Nothing else in the plugin makes network calls itself. Your own verify, deploy and prod-check commands reach whatever they reach.

|---|---|---|
| `builder` | Read, Edit, Write, Grep, Glob, Bash | 200 |
| `checker` | Read, Grep, Glob, Bash | 25 |

**What it never does**

## Limits

Each agent has a turn limit (`maxTurns` in its file), so a runaway agent stops. The values are about 1.5 to 2 times the most each agent needed across this plugin's own history (a builder phase took up to 148 tool calls, a checker run 12, a shipper run 9):

| Agent | `maxTurns` | Why |
|---|---|---|
| `builder` | 200 | A large phase is many reads, edits and test runs. |
| `checker` | 25 | A few commands and a short report. |
| `shipper` | 20 | A fixed runbook of commit, deploy, check and rollback. |
| `model-scout` | 15 | One search, up to 3 fetches and one write. |

When an agent stops at its limit, `run` stops too. It reports what was done and what is left, and never treats the partial result as complete. You can resume the phase. Partial output at the limit needs Claude Code v2.1.246 or later, which the stated minimum already covers. Treat the values as starting points and tune them from your own history.

A checker can report `UNFINISHED` or `TIMED OUT` for a command that was still running after its bounded wait (10 minutes, or 5 reads of a background output file). That is not a pass: `run` runs the command itself in the foreground and marks the row "(re-run in main)". The long-command rule is a prompt change, so a model can still ignore it.

The roadmap reader works on tables only, line by line: it is not a full Markdown parser, and it doesn't read the prose around the tables. It takes one file in one project. `standardize` and `restore` can't know that you said yes: the roadmap skill is the gate, and only you start it. The copies in `.roadmap-backups/` are local files on the same disk, not an off-machine backup, and the script never prunes them. Just before it replaces the roadmap file the script reads it again and stops if it changed since the command read it, which narrows the window when two sessions write the same file; it is not a lock, and a change landing in the last instant can still be lost (the kept copies hold the earlier versions).

The survey has limits of its own:
- **The script catches known secret shapes, not every secret, and not confidentiality.** It skips a file whose text matches a token or key format, a private key, a password, or a secret-looking name followed by a value, and it scans the finished survey and every printed line once more. A secret in a shape it does not know passes, and it cannot tell whether a sentence in a README or a plan file is confidential. The consent list is the control: you see the files first and can remove any.
- **The script reads only the allowlist; the assistant is held back by instructions, not a lock.** The script opens only the files on the confirmed list. The onboard skill, like any skill, runs in your assistant session, where the assistant keeps its normal tools; it is held back from reading other files by the skill's instructions, not by a lock (a skill's `allowed-tools` pre-approves tools, it does not remove any). Consent is an instruction the skill follows, backed by the digest, which proves the confirmed list is unchanged, not that you saw it. No guard rule enforces either. A team that cannot accept that should not run onboarding in an assistant session on client material.
- **The `.gitignore` inside `.phased-shipping/` protects git users only.** In a Perforce, Subversion, Mercurial or similar workspace, ignore the folder in that tool yourself before you run the survey.
- **Endpoint-security behaviour is unverified.** A script that lists and reads many files may trigger an alert or a block on a managed laptop. This has not been checked; if one appears, stop and ask your security team.
- **A monorepo is one project.** The survey reads the root folder's files, `docs/` and the plan folders, not each package's own manifest.
- **Symbolic links and junctions are skipped**, even ones that point inside the project.
- **The survey is a snapshot.** It is not updated by itself; run onboarding again after the project changes.
- **A survey that came with a cloned repository is untrusted.** The folder's `.gitignore` keeps an honest survey out of git, so a `.phased-shipping/survey.json` that git tracks was not made on your machine. Like a README, it is data: its commands are only proposals and nothing runs them. `show` keeps only the schema's fields from it, cleaned of control, line-separator, bidirectional, zero-width, tag and other Unicode format characters and cut to fixed lengths and list sizes, keeps a command, an action, a stack entry and a manifest or deploy file name only in the forms the script itself writes, drops everything else, and starts with a line saying it was read from disk and is data to confirm, not instructions.

`caught_by` in the history is only as good as the main session's attribution of each fix round or rollback to a check. An unclear source is recorded as the check that first reported it. Records made before 0.6.0 have no `caught_by` and are not backfilled.

The guard has limits of its own:
- **It can be switched off.** An organization policy that allows only managed hooks (`allowManagedHooksOnly`) blocks plugin hooks, unless an admin force-enables the plugin. `disableAllHooks` does the same. The probe shows which case you are in, run by run.
- **It needs node.** The hook runs `node`. If `node` isn't on the PATH, the plugin's hook can't start, and Claude Code lets the call go ahead, because the plugin's `hooks.json` can't set `onFailure: block` without blocking your main session as well. The same goes for a hook that times out (10 seconds). The personal copies do set `onFailure: block`, so a missing `node` stops the agent's calls there instead (v2.1.295 or later; on an older version the key is most likely ignored, and the hook then fails open).
- **It is not a sandbox.** It stops direct commands. It doesn't stop an agent from writing a script that pushes and then running it (`bash script.sh`, `source script.sh`), or from a command it can't see inside, such as a variable that holds a program name (`$CMD push`, still open). Text piped into a shell (`... | sh`) is denied, but a script file, `python -`, `node -e` and other interpreters that run text are not. A `.git` path built from a variable, glob or command substitution (for example `"$(git rev-parse --git-path hooks)/pre-commit"`) is not matched, only literal text. Text piped into `xargs` is not seen for the builder and checker (`echo deploy | xargs npx wrangler`, `echo push | xargs git`); the shipper is refused `xargs` outright. A flag or verb hidden in a variable is denied for the shipper's `git push`, `commit`, `revert` and `tag`, but not for `gh api`, `curl` or the deploy tools of the builder and checker (`V=deploy; wrangler $V`). Hooks defined outside `.git` and `.husky` (`lefthook.yml`, `.pre-commit-config.yaml`, a `package.json` script) are not protected. These stay open: closing them would deny most real work.
- **The lists are not exhaustive.** `git` and `gh` are allowlists, so an unknown form of those is denied. The publish and deploy lists are denylists, so a tool or flag that isn't listed gets through. The lists are an extra layer on top of the agents' own rules and `run`'s gates, which still apply; they are not a complete list of what could go wrong.
- **It over-denies on purpose.** An unclear form is denied, and a false deny costs the agent one retry. A builder that types `git commit` in a scratch repository to set up a fixture is denied, and so are `git reset HEAD file` (use `git restore --staged`), `git branch new-name` (use `git checkout -b`), `git commit-tree`, `git config user.name x`, a `$'..'` string, `{a,b}` braces, and any `gh` write. A test suite that commits inside its own temporary repositories, run as `npm test`, is not denied, because the guard sees only the command the agent types. The agent reports the denial instead of working around it.
- **A session started as an agent is restricted too.** `claude --agent phased-shipping:builder` makes the main session that agent, so the guard restricts it as well. That is the guard working as designed.
- **Seen firing in real runs, on one setup.** In this project's own runs on Windows with Claude Code 2.1.310, the checker's self-test probe was blocked at the start of recent runs, and once the guard denied a shipper command that is not on the shipper's git list (`git grep`). Both are in the maintainer's phase history (its `guard` field is `active`). That is the only setup it has been seen on: it has not been checked on macOS, on Linux or on other Claude Code versions. Elsewhere it is proven by feeding sample payloads to the scripts, in this repo's tests, which include a regression case for every gap an independent security review found. The `agent_type` field, the frontmatter `hooks:` block and `onFailure` come from the Claude Code docs and the release notes. Run the probe on your own setup to see whether it is active.

## Windows and Git Bash

- The agents run `npm`, `node` and `git` directly. In Git Bash, `cmd /c npm ...` prints only the cmd banner and runs nothing, so don't wrap commands in `cmd`. The guard may also block `cmd` and `powershell` for the agents.
- The main session records the timestamps (PowerShell `(Get-Date).ToUniversalTime()` on Windows when it has a PowerShell tool, otherwise `date -u`). The agents don't read the clock to make timestamps. The checker does report each command's duration, and it takes each exit code and each duration from one line (it runs every command as `SECONDS=0; <command>; echo "exit=$? seconds=$SECONDS"`). A local-time question, such as a no-deploy window, is for the main session to check with PowerShell.
- A long command can be moved to the background by the Bash tool once it passes its timeout (2 minutes by default, 10 at most). The checker passes the 10-minute timeout on every call.

## Install

From the library repo (Claude Code):

```bash
claude plugin marketplace add trbbmnglg/phasewright
claude plugin install phased-shipping@phasewright
```

To try it without installing: `claude --plugin-dir plugins/phased-shipping`

**If you can't use plugin marketplaces** (for example, your organization restricts them; check its policy first), you can install the plugin as personal skills and agents instead, from the repo root:

```bash
node scripts/sync-personal.mjs           # writes /ps-plan, /ps-run, /ps-roadmap, /ps-onboard and the ps-* agents into ~/.claude
node scripts/sync-personal.mjs --check   # reports drift
node scripts/sync-personal.mjs --remove  # removes them
```

Personal skills and agents aren't namespaced, so the copies get a `ps-` prefix. The script only overwrites or removes files it generated. History goes to `~/.claude/phased-shipping/`, and so do the guard scripts (`hooks/`). Each `ps-*` agent copy also carries a `hooks:` block that runs the guard.

**Other tools:** the skills load in VS Code Copilot and Cursor (they read `SKILL.md`), but model pinning and the four agents are Claude Code features.

## Customize

- **Different defaults:** edit `model:` and `effort:` in `skills/*/SKILL.md` and `agents/*.md`.
- **Pinning versions:** use aliases (`opus`, `sonnet`, `haiku`, `fable`) and pin versions with `ANTHROPIC_DEFAULT_*_MODEL`. That way the files don't go stale when models change.
- **Team conventions:** put your model convention in CLAUDE.md. The plan skill follows it over the scout's picks, unless a model is retired or unavailable.
- **Other providers:** on Bedrock, Vertex and Foundry the aliases can resolve to older versions. The Model check records what they resolve to.

## Test it

```bash
cd plugins/phased-shipping
claude plugin validate . --strict
claude plugin eval . --allow-tools WebSearch,WebFetch,Bash
```

The fifteen cases check that:
1. a multi-part request produces a phased roadmap with model and effort for each phase;
2. a typo fix doesn't trigger the plan skill;
3. tests, browser checks, commit and deploy are routed to the cheap tier;
4. a small feature becomes one phase with no roadmap round-trip;
5. `run` refuses to build when there is no plan;
6. `run` doesn't deploy in the turn that builds;
7. the shipper skips actions that have no `APPROVED:` line;
8. `run` shows a plan's commands and waits for your OK when the plan came with a cloned repo;
9. `run` treats a builder result that starts with `NO SHELL:` as unverified, and doesn't go on to the preview as if the checks had passed;
10. `/phased-shipping:roadmap check` reports a roadmap's problems and edits nothing;
11. `/phased-shipping:roadmap standardize` shows its diff and asks before it writes, even when told not to ask;
12. `/phased-shipping:roadmap restore` lists the kept copies or shows its diff and asks before it restores, even when told not to ask;
13. `/phased-shipping:onboard` shows the list of files and asks before it runs the survey, even when told not to ask;
14. `/phased-shipping:roadmap adopt` shows the proposed table and asks before it writes, and does not add a plan file that has no timestamps without a status you confirmed;
15. `run` asks once whether to turn the dashboard on, and never turns it on without your yes, even when told not to ask.

Cases 5 to 15 test the safety rules. They have not been run against a model yet, so expect to adjust their wording on a first run.

The guard has its own tests, which run in this repo's `npm test`: `node --test tests/guard.test.mjs tests/shell-split.test.mjs`. They feed sample hook payloads to the scripts; they don't need hooks to run.

Evals make real model calls on your account. Use `--ablation none` while you're iterating, to halve the cost.

## Cost notes

- **`plan`** has to be listed so Claude can invoke it on its own, so its short description is in context on every turn.
- **`run`** is manual-only, so it adds nothing to context until you invoke it. So are **`roadmap`**, **`onboard`** and **`dashboard`**. While the dashboard is on, the run makes about eight small `status.mjs` calls per phase; each is a no-op when it is off.
- **Agents:** their descriptions cost a little on every turn. Their full text loads only when they run.
- **Model check:** it refreshes only on events or after 30 days, so the web isn't searched on every phase.
- **Baseline:** this is one extra cheap check run, and it saves the fix rounds spent chasing failures that were already there.
